# 導入と停止 復旧の手順

現在はローカル検証用。Cloudflare資源の作成・デプロイ・本番接続は別の操作として扱う。

## 最初に決める内容

対象は読み取り専用JSON APIを一つ。認証済み主体、所属、許可レコードの判定元、
許可項目、最大本文サイズ、日次件数・バイト数、共有するbudget_group、停止時の運用担当を決める。
日次件数の設定は業務量から決め、デモの50件をそのまま本番へ適用しない。
入力契約と適用対象の一覧をレビューし、未設定ルートが保護済みと表示されないようにする。

## 段階的な導入

1. READMEの合成デモとローカル試験を実行する。
2. 実データを使わない検証環境で、認可結果の受け渡しを接続する。
3. `/v1/evaluate`で内容の契約違反を確認する。このAPIは本文を返さず、取得枠も確認・消費しない。
   評価APIの成功は防御有効化ではない。実トラフィックの自動収集・本文保存機能もない。
4. テスト利用者の対象ルートを`/v1/protect`へ接続する。戻り値をそのまま返し、元の本文へ戻さない。
5. 合意した負荷条件でp50/p95/p99、エラー率、CPU、メモリ、Objectへの偏り、課金対象の要求数・稼働時間・書込量を測る。
   許容値は既存APIのSLOと費用上限から決める。架空の改善率や一律の遅延保証を使わない。
6. 独立レビュー、設定レビュー、停止・復旧試験後に本番導入の判断を行う。

## Cloudflareへ配置する場合

利用者自身のアカウント内にRust WorkerとSQLite-backed Durable Objectsを配置する。
wrangler.tomlのworkers_dev=false、preview_urls=falseと公開routesなしを維持する。
呼出側だけにService Bindingを追加する。DO namespaceは呼出アプリへ直接渡さない。
SERVICE_ENABLEDとPOLICIES_JSONはレビュー済み設定で与え、認証キー・顧客データをポリシーに入れない。
コード・設定・namespace・契約の組み合わせを記録する。更新でnamespace名やbudget_groupを変えると枠を新設することになる。

`wrangler deploy`はこのリポジトリのCIでは実行しない。CloudflareのトークンやAPIキーをGitHubへ登録する必要はない。
将来の自動配布でも最小権限・人による本番反映判断を維持する。

## 障害時

503では対象データを返さない。まず設定・binding・DO到達性・リソース制限を、本文を出力せず確認する。
既知の正常版へロールバックする際も同じDO namespaceとbudget_groupを維持する。
ガードを停止する場合は対象APIを503またはメンテナンス状態にする。停止中に元のデータを直接返さない。
429は権限失敗ではなく取得枠不足。誤設定を修正する場合は既消費量を維持し、変更理由を記録する。
ストレージの巻き戻し・削除を復旧手段にしない。必要な場合は枠が復活する影響を個別判断する。

## 依存と更新

Rust 1.95.0、worker/worker-build 0.8.7、Node 26.9.0を初期検証環境とする。
Cargo.lockとpackage-lock.jsonを固定し、Dependabotによる提案は検証後に手動で取り込む。
MiniflareはWrangler 4.147.0同梱系列5.20261001.0-alphaを使う。プレリリースの開発用依存であり、
Cloudflare本番の動作保証として扱わない。

Miniflareが固定するsharp 0.35.4には[GHSA-wq5f-xc86-pv6w](https://github.com/advisories/GHSA-wq5f-xc86-pv6w)があるため、
開発依存のsharpを修正済み0.35.5へpatch overrideしている。無視設定や監査除外は使わない。
上流が修正版を採用したらoverrideの必要性を再評価する。画像処理機能は製品に使用しない。
開発依存も含めてnpm auditを実行する。
